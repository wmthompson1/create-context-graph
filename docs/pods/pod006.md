### Ready-to-run 5-minute demo script for the PM

This script is designed to feel like a live product demo, not a technical readout. It keeps the story anchored on the manufacturing work-order ontology and ends with a confident statement that the system is evidence-bound, read-only, and GDS-free.

---

#### 00:00–00:35 — Set the stage

**Goal:** Show that this is a manufacturing reasoning system, not a generic chatbot.

**Speaker notes:**
- Open with the business problem: “The real issue is not retrieving a document. It is connecting operations data so the agent can explain what is happening and why.”
- Start from the v1.1 ontology: 12 classes, 14 object properties, and 10 datatype properties.
- Point to the namespace and one example class to anchor the conversation.

**What to say:**
- “We are showing a GDS-free, ontology-backed manufacturing reasoning agent.”
- “The model is centered on the work order, which links material requirements, schedule slots, machine capacity, production events, and supplier commitments.”
- “This is the structure behind the operational story: WorkOrder, BOM, MaterialRequirement, Part, WorkCenter, ScheduleSlot, ProductionEvent, Supplier, and SupplyCommitment.”

**Reference example:**
- “saltmfg:BillOfMaterials a owl:Class ; rdfs:label \"Bill of Materials\" .”

---

#### 00:35–01:20 — Work-order ontology walkthrough

**Goal:** Make the ontology feel intuitive and operationally grounded.

**Speaker notes:**
- Treat the work order as the anchor object in the graph.
- Walk the graph logically instead of listing classes mechanically.
- Explain that the point is not the ontology for its own sake; it is the ability to answer operational questions with explicit evidence.

**Walkthrough:**
- “A WorkOrder is the center of the story.”
- “It references a BillOfMaterials, which defines required parts through MaterialRequirement nodes.”
- “Those requirements connect to specific Part records and to the work center or machine responsible for execution.”
- “ScheduleSlot nodes show the planned timing and capacity for that work center.”
- “ProductionEvent nodes record what happened on the line as the order moved through execution.”
- “Supplier and SupplyCommitment nodes connect the planning side to the delivery side, so we can ask whether supply coverage is adequate.”

**Simple path to emphasize:**
- WorkOrder → BillOfMaterials → MaterialRequirement → Part
- WorkOrder → assignedTo → WorkCenter
- WorkCenter → hasScheduleSlot → ScheduleSlot
- ProductionEvent → occursOn → Machine
- SupplyCommitment → covers → Part

**Key PM line:**
- “This is not just a database record. It is a connected operational model that allows the agent to explain dependencies, schedule risk, and material coverage from the graph itself.”

---

#### 01:20–02:00 — Ontop + synthetic mapping sanity check

**Goal:** Prove the ontology is executable and not just a diagram.

**Speaker notes:**
- Open the OBDA mapping and point out that it is synthetic, metadata-only, and SAP-free.
- Run the smoke SPARQL query so the demo feels concrete and validated.
- Keep this section brief and crisp.

**What to show:**
- “mappingId class-billofmaterials … source SELECT 1 AS synthetic_row”
- “SELECT ?resource WHERE { ?resource a saltmfg:KnowledgeBase . }”

**What to say:**
- “The ontology is executable through Ontop against a synthetic metadata layer. It is intentionally isolated from SAP, CDS, and transactional sources.”
- “The goal here is to validate the ontology contract and reasoning model without touching production systems.”

---

#### 02:00–03:00 — Context-graph package and reasoning design

**Goal:** Show the packaged implementation and the no-GDS constraint.

**Speaker notes:**
- Open the context-graph manufacturing package directory.
- Point to the three key artifacts: domain model, tool catalog, and reasoning strategies.
- Call out that the execution engine is parameterized read-only Cypher and that there are no gds.* calls.

**What to show:**
- domain.yaml
- tools/manufacturing-tools.yaml
- reasoning/strategies.yaml

**What to say:**
- “This package defines the operational graph and the bounded reasoning strategies that can act on it.”
- “The system is intentionally limited to read-only Cypher. It has no graph projection, no GDS dependency, and no inferred edge creation from weak signals.”

**PM framing:**
- “This makes the system easier to trust in enterprise settings because the logic is explicit, explainable, and bounded.”

---

#### 03:00–04:20 — Live Strands agent interaction

**Goal:** Show the agent answering a manufacturing question using explicit evidence.

**Primary demo path:** BOM requirements

**Prompt to ask:**
- “For WorkOrder X, what parts are required and through which BOM?”

**What the agent does:**
- runs the bom_requirements strategy
- resolves the path WorkOrder → BillOfMaterials → MaterialRequirement → Part
- returns explicit node IDs and relationship types
- explains the answer in plain language with evidence citations

**Speaker notes:**
- Keep the output concrete and short.
- Show that this is not a free-form answer; it is a graph traversal backed by actual edges.
- If possible, highlight the evidence chain in the output: work order ID, BOM ID, material requirement nodes, and part nodes.

**What to say:**
- “This is the product moment. The agent is not guessing. It is reading the graph, following the BOM path, and answering from explicit relationships.”

**Optional second path if time allows:**
- “Are there overlapping schedule slots for WorkCenter Y tomorrow?”
- Agent runs the schedule_contention strategy and compares ScheduleSlot intervals for a single work center.
- Show the answer as either contention or no contention with evidence.

---

#### 04:20–05:00 — Close with boundaries and next steps

**Speaker notes:**
- End on trust and operational safety.
- Reiterate the boundaries: read-only, evidence-bound, no inferred edges from names or timestamps, no GDS, no SAP/CDS/transactional ingestion.
- Mention future work briefly: richer fixtures, more strategies, additional frameworks beyond Strands.

**What to say:**
- “This is a safe manufacturing reasoning workflow: it reads explicit evidence, explains the path, and does not invent relationships.”
- “The next step is broader fixture coverage and additional strategy expansion, but the core product story is already clear.”

**Closing line:**
- “We are not building a generic chatbot; we are building an evidence-backed manufacturing reasoning layer that can connect work orders, materials, schedules, and suppliers in a way that is explainable and operationally relevant.”
