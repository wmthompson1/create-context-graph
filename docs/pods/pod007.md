

# **Demo Output 04 — Production Lineage Example**

## Scenario

User asks:  
**“Walk me through the production lineage for WorkOrder WO‑2048 — what events occurred, in what order, and which parts were consumed or produced?”**

## Evidence path

ProductionEvent → executesWorkOrder → WorkOrder  
ProductionEvent → precedesEvent → ProductionEvent  
ProductionEvent → consumesPart / producesPart → Part

From the ontology:  
> “saltmfg:precedesEvent a owl:ObjectProperty ; rdfs:domain ProductionEvent ; rdfs:range ProductionEvent.”  
> “saltmfg:consumesPart a owl:ObjectProperty … rdfs:label ‘consumes part’.”  

These explicit edges form the backbone of execution reasoning.

## Output summary

The agent reconstructs the event sequence and material flow using **only explicit graph evidence**.

- WorkOrder: `WO‑2048`
- ProductionEvents:
  - `PE‑2048‑01` — consumes `P‑1001`
  - `PE‑2048‑02` — consumes `P‑1002`, produces `P‑2001`
  - `PE‑2048‑03` — produces `P‑3001`
- Event order:
  - `PE‑2048‑01` → `PE‑2048‑02` → `PE‑2048‑03`

## Example response

“For WorkOrder WO‑2048, the production lineage consists of three explicitly linked events.  
Event PE‑2048‑01 precedes PE‑2048‑02, which in turn precedes PE‑2048‑03.  
The graph shows that PE‑2048‑01 consumes part P‑1001, PE‑2048‑02 consumes P‑1002 and produces P‑2001, and PE‑2048‑03 produces P‑3001.  
This lineage is derived entirely from explicit `executesWorkOrder`, `precedesEvent`, `consumesPart`, and `producesPart` relationships.”

## Why this matters

This demonstrates execution‑flow reasoning — the third pillar of manufacturing intelligence:

- explicit event sequencing  
- material flow visibility  
- explainable process understanding  
- no inference from timestamps or naming patterns  
- no GDS, no heuristics, no speculation  

## PM talking point

“This is where the agent starts to feel like a digital process engineer — it can walk through the actual execution chain of a work order using explicit evidence, not guesswork.”
